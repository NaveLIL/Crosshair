# Blue Angel: исследование загрузки Crosshair через HaRET

Дата: 16 октября 2026. Этап D, локальный статический анализ; устройство не подключалось, HaRET и образы на КПК не запускались.

**Результат:** найден и закреплён контракт исходного загрузчика; отдельный ARM flat binary адаптер Crosshair с входом по физическому адресу `0xa0008000` реализован, собран и проверен статически на ПК. Это адрес, полученный из исторических исходников, а не разрешённая для экспериментальной записи область конкретного работающего КПК. Совместимость с скачанным HaRET на уровне всего бинарника и безопасность аппаратного запуска пока не доказаны. ELF напрямую этим путём не загружается.

Статусы: **АРТЕФАКТ** — проверено на локальном файле; **ДОКУМЕНТ** — подтверждено первоисточником; **ПРОЕКТ** — выбранный дизайн, аппаратно не проверенный; **ГИПОТЕЗА** — требует проверки; **НЕИЗВЕСТНО** — доказательств недостаточно.

Отдельное ограничение: `RAMADDR=0x80000000` из модели ROM-анализатора **не относится** к этому загрузочному контракту. Адрес образа ROM, адрес WinCE VA, PA RAM и MMIO должны храниться раздельно.

### Размеры и выравнивание

H08 `linboot.cpp:147–149,385–395` использует шесть индексных страниц по 1024 указателя; при странице 4096 байт формальный предел суммарных округлённых до страницы kernel+initrd — 24 MiB. Это предел таблицы указателей, **не разрешённый размер аппаратного эксперимента** и не проверка допустимых областей RAM. Initrd размещается лишь на 5 MiB выше entry (`0xa0508000` при указанной базе), поэтому большой kernel может пересечься с initrd значительно раньше этого максимума.

Файл произвольной длины читается по фактической длине, но relocation копирует последнюю страницу целиком (`linboot.cpp:199–211,269–272`). Для Crosshair предлагается ненулевой `.bin`, начало/entry кратное 4 и выравнивание файла нулями до 4096 байт для детерминированного хвоста. Последнее — наш консервативный формат артефакта, не обнаруженное требование HaRET к длине файла. Собственные linker assertions должны проверять раздельность tags, загружаемого диапазона, BSS, стека и диагностической записи. Initrd для Boot 0.1 не нужен. Короткая или пустая CMDLINE предпочтительна: старый `setup_linux_params` копирует её в фиксированную страницу tags без общего проверенного протокола произвольной длины.

### `startup.txt`: значения и момент выполнения

`startup.txt` запускается при старте GUI HaRET; это подтверждено не только wiki, но и H08/H09 `src/wince/haret.cpp:64–65`. Следовательно, наличие в нём `boot` может начать handoff уже при запуске EXE. Этот проект не создаёт готовый к случайному автозапуску файл для физического устройства.

| Переменная / команда | Роль для будущего Crosshair-пакета |
|---|---|
| `KERNEL` | Имя **flat `.bin`** с ARM entry по первому байту, не `.elf`. Имя `zImage` в старых пакетах — соглашение, не проверка формата загрузчиком. |
| `MTYPE` | `766` как historical Blue Angel identity; адаптер сохраняет входное значение в `CROSSHAIR_BOOT_RECORD.incoming`, но пока не валидирует соответствие `766`. |
| `RAMADDR`, `RAMSIZE` | Явные значения из исследованного профиля помогают исключить ошибку autodetect, но предварительно нужны проверка аппаратного профиля и разрешение на конкретный запуск. |
| `INITRD` | Пусто; Crosshair Boot 0.1 rootfs не использует. |
| `CMDLINE` | Не нужен Linux `root=`, `init=`, `console=`: собственное ядро их не реализует. Можно оставить пустую строку. |
| `FBDURINGBOOT` | Управляет выводом **самого HaRET** в найденный framebuffer; не создаёт драйвер LCD Crosshair. Для наиболее ограниченного handoff разумен `0`, но пригодность диагностики согласуется отдельно. |
| `KERNELCRC` | Предусмотрен source для проверки скопированных байтов; сообщения CRC failure в просмотренном preloader сами по себе не гарантируют остановку. |
| `KERNEL_OFFSET` | Есть в H09, отсутствует в H08 и не обнаружен среди строк скачанного EXE. Предварительный адаптер использует фиксированный `+0x8000`, не требует этой переменной. |
| `boot` | Передача управления; не выполнялась и не включена в автоматический сценарий проекта. |

## 4. Реализованный адаптер и граница проверки

**РЕАЛИЗОВАНО И ПРОВЕРЕНО СТАТИЧЕСКИ НА ПК; АППАРАТНО НЕ ПРОВЕРЕНО.** Отдельная конфигурация Blue Angel собирается командой `scripts/build.sh blueangel`. `src/bsp/blueangel.rs` использует собственный 96-byte `BLUEANGEL_RAM_LOG`; VersatilePB и его PL011 драйвер исключены из этой сборки feature selection. Blue Angel код не содержит UART/GPIO/LCD/Flash/Radio MMIO.

Общий `src/arch/entry.S` входит в ARM state по контракту загрузчика, устанавливает `CPSR_c=0xd3` (SVC, IRQ/FIQ masked), собственный выровненный стек и очищает BSS 32-bit записями. `r0–r2` до вызова `rust_main` не изменяются. В Rust выполняются volatile проверки очищенного BSS и инициализированного `.data`, входные регистры сохраняются как числа, не разыменовываются. Общая структура `CROSSHAIR_BOOT_RECORD` имеет C layout, magic, stage, incoming, length и 96-byte message. Успешный путь Blue Angel записывает баннер в оба ограниченных RAM буфера, устанавливает stage 2 и уходит в `kernel_idle`. Panic пишет stage 3 и фиксированное сообщение. Ожидание — бесконечная ветка ARM `b kernel_idle`, без реализации сна PXA и без обещаний энергосбережения.

`link/blueangel.ld` задаёт origin `0xa0008000` с собственным бюджетом 1 MiB; `link/sections.ld` размещает `.text/.rodata/.data`, NOLOAD `.bss`, собственный NOLOAD stack 16 KiB и содержит assertions ARM word aligned entry, stack 8-byte alignment и общего бюджета. Это самоналоженный лимит образа, не установленная свободная область WM.

| Артефакт / наблюдение сборки | Проверенный результат |
|---|---|
| `target/artifacts/blueangel/crosshair-boot.elf` | Статический ELF32 little-endian ARM EABI5, ARMv5TE, entry `0xa0008000`, без undefined symbols и dynamic loader. Для анализа и отладки. |
| `crosshair-boot.bin` | 500 байт в текущей сборке; данные каждого PT_LOAD совпадают с соответствующим диапазоном flat file. Первый байт — ARM entry, не ELF header. |
| `crosshair-haret.bin` | 4096 байт; flat file с явным нулевым дополнением до страницы. Заголовок zImage/Linux decompressor не требуется исследованным загрузочным путём. |
| `image.json`, `elf-report.txt`, `disassembly.txt`, `size.txt` | Манифест hashes, реальные ELF headers/attributes и инструкции текущей сборки. Параметры могут измениться после пересборки; источником актуальных адресов остаётся ELF/manifest. |
| Собственный RAM extent | `[0xa0008000,0xa000c2d0)` = 17 104 байта, включая padding и stack 16 KiB; это не размер файла. |
| BSS / stack текущей сборки | BSS `[0xa00081f8,0xa00082d0)`; stack `[0xa00082d0,0xa000c2d0)`, stack top кратен 8. |

Независимая статическая сверка в этой работе прочитала ELF PT_LOAD, проверила соответствие flat segment bytes, актуальные hashes манифеста, нулевой tail padded image, выравнивание BSS, отсутствие overlap BSS/stack и собственный бюджет линкера. Код `entry.S`, RAM diagnostics и фактический disassembly просмотрены отдельно. Адаптер не запускался на КПК; его ARM-код в физической памяти Blue Angel пока не исполнялся.

Наличие собранного `.bin` и RAM diagnostic record **не означает наблюдаемый аппаратный boot**: чтение этой записи после зависания/сброса ещё не обеспечено. Результаты нормального и panic пути QEMU VersatilePB описаны в BUILDING.md/BOOT.md и основном отчёте. Они доказывают выполнение общего entry/Rust-кода на другой плате; не проверяют HaRET, XScale, физическую RAM и периферию Blue Angel.

До аппаратной попытки требуется довести сверку выбранного HaRET EXE с исходным контрактом до полного пути (или собрать известный source), утвердить RAM layout с учётом BSS/stack и состояния WM, обеспечить канал наблюдения и процедуру возврата. Реальный запуск остаётся отдельной процедурой с разрешением владельца.

## 7. Возврат к заводской системе и предел слова «безопасно»

Нормальный HaRET `boot` является передачей владения RAM/CPU, а не вызовом приложения, из которого допустим `return`. Физическое копирование образа и tags может уничтожить страницы пользовательского хранилища WM2003; masking interrupts, изменение MMU mapping и shutdown периферии также не обратимы одним `bx lr`. Функция `return_control()` лишь re-enables interrupts и не восстанавливает RAM, MMU и DMA.

План возврата — штатный сброс с загрузкой сохранённой заводской ROM и при необходимости восстановление **заранее проверенной** резервной копии RAM-состояния. Конкретная последовательность soft reset/hard reset на единственном экземпляре и сохранность RAM после неё в этой работе не проверялись. Нельзя обещать сохранение пользовательской сессии или заменять резервную копию ROM installer. Не нужно повторно прошивать аппарат ради подготовки первого RAM boot.

Предпосылки будущего отдельного разрешения: зафиксированные backup/restore пользовательских данных, штатно работающее питание без изменения его электроники, проверенный способ сброса и возврата, статически сверенный выбранный HaRET и образ с хешами, ограниченный RAM layout, понятный канал наблюдения, отсутствие Flash/Radio/SD raw writes. Разрешение на такую конкретную процедуру ещё не получено; текущая задача его не подразумевает.

## 9. Частичная сверка инструкций скачанного HaRET

**АРТЕФАКТ:** разобраны только три заранее ограниченных диапазона `.text` закреплённого EXE: копирование слов, preloader, MMU trampoline — 192 ARM инструкции. Средства: `pefile==2024.8.26`, `capstone==5.0.6`. Собственный воспроизводимый инструмент находится в `tools/inspect_haret_static.py`, зависимости — в `tools/requirements-haret.txt`. Он принимает `INPUT OUTPUT`, читает не более 144 385 байт, проверяет закреплённый SHA-256 до импорта PE-библиотек и разбора PE, затем проверяет Machine, границы и ожидаемые инструкции. PE не исполняется. Выход создаётся исключительно как новый файл; существующий файл не заменяется. Проверки работают и при `python -O`.

Первый архивный результат `local/references/pxadroid/haret-static-evidence.json` (SHA-256 `e2dded234f1853a203b0c9291b0613d88a2e3b6b08dbbcb4ed64c125057287d0`) и исходный reference manifest сохранены без изменения. Новым инструментом получен `local/haret-static-evidence-tool.json`, SHA-256 `ed78f2be206b42c8ab8822e995c3e22c680c44c047c9e71a8c2f7f5faf1685f3`; отличие JSON связано с нормализованным полем имени входа. Проверены 192 инструкции и отрицательные случаи: неверный SHA отклоняется до разбора/импорта библиотек без создания результата; существующий output отклоняется без изменения байтов. Хеш исходного EXE после проверок прежний.

Следующие VA — **preferred VA файла PE при ImageBase `0x10000`**, до relocation HaRET. Это не физические адреса КПК и не адреса собственного ядра.
